PyTorch09-PyTorch模型部署

九、PyTorch模型部署

到目前为止，我们已经初步掌握了如何用 PyTorch 框架实现与训练神经网络模型，也学习如何在训练环境下做推理、将模型文件保存下来。但很多时候，我们在软硬件环境A下训练与保存得到了模型文件，实际使用时可能无法还原当时训练环境A中的软硬件，甚至要求使用与训练环境A完全不同的另一套软硬件环境。此时我们可能会想，有没有一种类似于 Java 虚拟机一样的东西能让编译好的 Java 字节码到处运行，我们只要在实际使用中将恢复或搭建一个兼容的 Java 虚拟机 环境即可运行已有的 Java 字节码（其实就是 Java 程序的一种保存形式，是其编译得到的内容）。

可喜地是，在神经网络模型的生态环境内，确实存在一个类似于 Java 虚拟机环境的开源解决方案，它就是 ONNX ，它将使用PyTorch框架实现的神经网络模型 转换成 .onnx 格式文件。与此同时，与之配套使用的还需要解析与运行 .onnx 格式文件的推理引擎及加速硬件。

本节学习的主要内容包含：ONNX的介绍与使用、推理引擎ONNX Runtime的介绍与使用、其他推理引擎。

9.1 ONNX的介绍与使用

9.1.1 ONNX的介绍

ONNX 官网：https://onnx.ai/ 。 ONNX GitHub代码仓库地址：https://github.com/onnx/onnx 。

ONNX（Open Neural Network Exchange，开放式神经网络交换） 是由微软、Meta 等机构在2017年共同创立的开源AI生态标准，旨在建立一个通用的模型文件格式。它充当了不同深度学习框架（如 PyTorch、PaddlePaddle 等）与各类硬件推理引擎之间的“跨平台桥梁”。通过将训练好的神经网络模型导出为统一的 .onnx 计算图格式，开发者能够实现“一次训练，到处部署”，轻松将模型运行在 ONNX Runtime、TensorRT、华为昇腾Asend 等多样化的软硬件生产环境中。

目前支持将神经网络模型转换成 ONNX 格式的深度学习框架，如下图所示：

ONNX 本质上只是一个“中间格式”（IR，Intermediate Representation），它就像是一份用统一标准绘制的建筑蓝图。这份蓝图本身是不能直接在硬件上运行的，它必须通过各家硬件厂商自己开发的推理引擎或编译器来进行解析、编译和执行。

ONNX 目前得到了 广泛支持，并被应用于众多框架、工具和硬件中。它能够实现不同框架之间的互操作性，并简化从研究到生产的流程，从而加速人工智能领域的创新，支持ONNX的推理引擎如下图所示：

基于ONNX标准，硬件厂商与软件厂商（一般来说提供加速硬件设施的硬件厂商也会同时开发出对应的推理引擎）只需要在自己的硬软件环境中实现 ONNX 文件的解析、运行与性能优化，就能把用其他深度学习框架开发的神经网络模型运行在自己自家软硬件产品上，实现生态融合与产品推广。

9.1.3.3 ONNX可视化

9.1.3.3.1 Netron 介绍

前面所述，通过TensorBoard可以对模型结构与输出特征图进行可视化。onnx将深度学习模型导出为".onnx"格式文件后，也有一个类似的开源项目 Netron 可以对".onnx"格式代表的模型进行可视化。

Netron 是一个用于查看神经网络、深度学习和机器学习模型的工具。

Netron 支持 ONNX、TensorFlow Lite、PyTorch、torch.export、ExecuTorch、TorchScript、TensorFlow、Core ML、OpenVINO、Keras、Caffe、Darknet、Safetensors 和 NumPy。Netron 对 MLIR、JAX、GGUF、RKNN、ncnn、MNN、PaddlePaddle 和 scikit-learn 提供实验性支持。

9.2.1 模型训练到跨平台部署

下图展示了”深度学习框架开发神经网络模型（训练阶段）、将各框架的模型统一导出为中间表示（桥梁与标准化阶段）、具体的推理引擎解析运行模型的中间表示（生产与运行阶段）“ 这三个阶段的示意与经典代表，描绘了现代深度学习模型从训练到跨平台部署的完整生命周期与流水线（Pipeline）：

上图的具体解释如下： 1. 深度学习框架（左侧：训练阶段）

  • 代表工具：PyTorch、TensorFlow、Caffe、MxNet 等。
  • 核心任务：在这个阶段，开发者使用各种主流框架编写代码、设计网络结构，并在服务器或集群上使用海量数据进行模型训练（Training），获取具有预测能力的权重。
  1. 中间表示 / IR（中间：桥梁与标准化阶段）
  • 代表格式：ONNX、TorchScript、Caffe 内部格式等。
  • 核心任务：由于不同的训练框架格式不通，无法直接在生产环境中高效运行，因此需要通过“转换”将各框架的模型统一导出为中间表示（Intermediate Representation, IR）。其中，ONNX 就是最核心、最通用的标准中间格式。在这个阶段还可以对计算图进行初步的优化。
  1. 推理引擎（右侧：生产与运行阶段）
  • 代表工具：TensorRT、ONNX Runtime、PaddleInference、NCNN、OpenVINO 等。
  • 核心任务：将标准化的中间表示（如 ONNX 文件）输入到具体的推理引擎中。推理引擎会针对不同的硬件（CPU、GPU、NPU 等）进行深度的算子融合与编译优化，最终在生产环境中高效地运行（Inference）推理任务。

9.2.2 ONNX Runtime的介绍与使用

9.2.2.1 ONNX Runtime的介绍

ONNX 官网：https://onnxruntime.ai/ 。 ONNX GitHub代码仓库地址：https://github.com/microsoft/onnxruntime 。

ONNX Runtime是一个跨平台的推理和训练机器学习的加速器。 ONNX Runtime 推理能够加快用户体验并降低成本，它支持来自 PyTorch 和 TensorFlow/Keras 等深度学习框架以及 scikit-learn、LightGBM、XGBoost 等传统机器学习库的模型。ONNX Runtime 与不同的硬件、驱动程序和操作系统兼容，并通过在适用情况下利用硬件加速器以及图优化和转换来提供最佳性能。

ONNX Runtime一般与ONNX搭配使用，将由ONNX导出的".onnx"格式的文件输入给ONNX Runtime这一推理引擎，实现不同深度学习框架模型的到处部署与推理。

9.2.2.2 ONNX Runtime的安装

官方提供的安装文档：https://onnxruntime.ai/docs/install/。

ONNX 与 ONNX Runtime 的兼容性矩阵见： ONNX 与 ONNX Runtime 的兼容性矩阵。

其他硬件加速设备、不同开发语言和应用场景等下的相关安装细节，请参考https://onnxruntime.ai/docs/install/。

ONNX 与 ONNX Runtime 兼容核心规则

  • 向后兼容（Backwards Compatibility）：所有版本的 ONNX Runtime (ORT) 都能运行早期标准下导出的模型（支持低至 opset 7 及以上的模型）。 1, 2
  • 向前兼容/上限约束（Forward Compatibility）：模型的 opset 版本 不能超过当前使用的 ONNX Runtime 版本所支持的最高 opset 范围。如果导出的 opset 高于运行时支持的上限，会直接抛出模型加载失败错误。 1, 2
  • 独立演进机制：ONNX 规范（Opset / IR 版本）与 ONNX Runtime 软件版本按不同周期独立迭代（ONNX 通常约4个月发布一次，ORT 按季度发布）。 1 #### 9.2.2.3 ONNX Runtime的使用

9.2.3 其他推理引擎

前面介绍的 ONNX Runtime 是运行 ONNX 模型的一种通用推理引擎，但并不是唯一选择。实际部署时还会遇到其他推理运行时、模型格式和编译工具链。

这三类概念很容易混淆，先作一个区分：

类型 作用 例子
推理运行时 / 引擎 读取模型、调度算子并在目标硬件上执行推理 ONNX Runtime、TensorRT、OpenVINO、ExecuTorch、llama.cpp
模型格式 / 中间表示 保存计算图、权重或二者的信息，供某个运行时读取 ONNX、Core ML、.tflite、GGUF、OpenVINO IR
编译器或编译基础设施 将模型图进一步优化、编译为特定硬件可执行的程序或库 torch.compile/Inductor、AOTInductor、IREE、Apache TVM

因此，ONNX 并不等同于 ONNX Runtime：前者是模型的中间表示，后者是能够执行该表示的一种运行时。对于常见的计算机视觉、语音和传统机器学习模型，ONNX 仍是非常成熟的跨框架交换格式；但它不是所有场景下的唯一答案，尤其是端侧部署和大语言模型部署往往需要结合目标硬件与运行时重新选择。

9.2.3.1 PyTorch 原生生态路线

当训练、部署都以 PyTorch 为主，并且不急于把模型交给其他框架或语言时，可以优先考虑 PyTorch 原生方案。

  1. torch.compile 与 Inductor

    • 是什么：torch.compile() 是 PyTorch 2.x 提供的图捕获与编译入口，默认通常使用 Inductor 生成并优化后端代码。
    • 适合什么：希望在现有 Python/PyTorch 推理代码上较少改动地获得优化时，可以先尝试它。
    • 要注意什么：它主要优化“当前 PyTorch 进程中的执行”，不是把模型保存为一个可被任意运行时读取的通用模型文件；模型可导出性、首次编译开销和实际加速效果都应在目标环境中测试。

  2. AOTInductor（Ahead-Of-Time Inductor）

    • 是什么：AOTInductor 可将通过 torch.export 得到的计算图预先编译并打包，面向不希望在部署端再进行即时编译的场景。
    • 适合什么：部署环境与训练框架仍围绕 PyTorch，但希望使用预编译产物、减少部署端 Python 依赖或启动期编译开销时。
    • 要注意什么：它更接近 PyTorch 自身的部署工具链，而不是 ONNX 的通用替代品；具体支持的硬件、Python/C++ 调用方式应以对应 PyTorch 版本文档为准。

  3. ExecuTorch

    • 是什么：ExecuTorch 是 PyTorch 面向端侧（edge）的运行时与部署工具链，可将模型经 torch.export 等流程处理后交给移动端、嵌入式设备等受资源约束的平台执行。
    • 适合什么：目标是 Android、iOS、嵌入式 Linux 或特定边缘硬件，并且希望保持 PyTorch 模型开发流程时。
    • 要注意什么：它的目标是端侧运行，模型算子覆盖、量化方案和硬件后端与服务器端 PyTorch/ONNX Runtime 不完全相同，部署前需要检查目标后端是否支持模型中的算子。

9.2.3.2 大语言模型（LLM）与生成式 AI

LLM 推理除了模型前向计算外，还需要处理分词器、连续生成、批处理调度和 KV Cache（保存已生成 token 的注意力键值）等问题。因此，除了通用 ONNX 路线外，也出现了针对 LLM 的格式与运行时。

  1. GGUF 与 llama.cpp

    • GGUF 是什么：GGUF 是常见于 llama.cpp 生态的模型文件格式，通常将量化后的权重、模型元数据和分词器相关信息放在一个文件中。
    • llama.cpp 是什么：llama.cpp 才是读取 GGUF 并执行推理的运行时/项目；GGUF 本身不是推理引擎，也不是像 ONNX 那样的通用计算图交换标准。
    • 适合什么：在个人电脑、CPU 或消费级 GPU 上离线运行经过量化的 LLM，且更重视内存占用和易用性时，GGUF + llama.cpp 是常见选择。

  2. Safetensors 与 Transformers 生态

    • Safetensors 是什么：Safetensors 是安全、高效地保存张量权重的文件格式，常与 Hugging Face transformers 一起使用。
    • 它不是什么：它通常不保存完整计算图，也不提供推理执行能力，因此不能单独视为 ONNX、GGUF 或 ONNX Runtime 的替代品。
    • 如何运行：还需要与模型配置、分词器和实际运行模型的代码/运行时配合，例如 transformers、vLLM、SGLang 或 TensorRT-LLM 等。

  3. LLM 服务端运行时

    • vLLM、SGLang：面向服务端高并发生成场景，重点处理连续批处理、KV Cache 管理与吞吐量；它们不是模型文件格式。
    • TensorRT-LLM：面向 NVIDIA GPU 的 LLM 优化工具链与运行时，适合对 NVIDIA 平台性能有较高要求的部署场景。
    • ONNX 仍可使用：ONNX 并没有因为 LLM 而失效；例如 ONNX Runtime 也提供面向生成式 AI 的相关能力。实际选择应由模型规模、目标硬件、量化方案和服务并发需求共同决定。

9.2.3.3 面向特定平台的运行时与模型格式

这类方案通常能更充分地利用某家厂商的硬件，但可移植性一般弱于 ONNX。

方案 主要目标平台 适合场景与说明
Core ML（.mlmodel / .mlpackage） Apple 的 iOS、iPadOS、macOS、watchOS 等 Apple 平台的官方机器学习框架。通过 Core ML Tools 等工具转换模型后，可由系统根据设备能力调度 CPU、GPU 与 Apple Neural Engine。
LiteRT / TensorFlow Lite（.tflite） Android、嵌入式及移动端 LiteRT 是 TensorFlow Lite 演进后的名称；.tflite 仍是常见模型文件扩展名。它主要服务 TensorFlow/Keras 生态，也常用于移动端量化模型。
OpenVINO 与 OpenVINO IR（.xml / .bin） Intel CPU、GPU、NPU 与部分 VPU Intel 的推理工具链。OpenVINO 可以读取 ONNX 等模型；在其部署流程中也常使用 IR 形式与设备相关优化。
TensorRT NVIDIA GPU NVIDIA 的高性能推理优化器与运行时，可从 ONNX 等来源构建 TensorRT engine；适合模型与部署硬件均固定为 NVIDIA GPU 的场景。

平台专用方案并非“绝对更快”。能否加速以及加速幅度会受到模型结构、输入大小、量化方式、设备型号和运行时版本影响，应使用真实模型在目标设备上基准测试。

9.2.3.4 编译器级开源方案

这类项目更接近“把模型编译成目标设备程序”的工具链。它们通常比直接使用 ONNX Runtime 更灵活，但接入、调试和硬件适配成本也更高。

  1. MLIR

    • MLIR（Multi-Level Intermediate Representation，多级中间表示）是一套编译器基础设施，不是可直接拿来加载模型并推理的终端运行时。
    • 它用于在不同抽象层次表示与优化程序，许多编译器项目会在内部使用它。

  2. IREE

    • IREE 是基于 MLIR 的机器学习编译器与运行时，可将模型编译到多种硬件后端。
    • 更适合有跨硬件编译、定制运行时或较深工程优化需求的团队；对于刚开始部署常规模型的学习者，ONNX Runtime、OpenVINO 或平台官方工具通常更容易上手。

  3. Apache TVM

    • TVM 是另一套开源机器学习编译器栈，能够针对不同硬件生成与优化算子实现。
    • 它适合研究编译优化或需要适配特殊硬件的场景；使用时需要投入更多时间处理模型导入、算子支持、调优与部署集成。

9.2.3.5 总结与选型建议

没有“所有场景都最好的推理引擎”。可以先按“模型类型、目标设备、是否跨框架、性能目标和团队维护成本”缩小范围，再用真实模型测试确认。

典型需求 可优先了解的方案 选择原因
常规 CV、语音或传统机器学习模型，需要跨框架/跨语言部署 ONNX + ONNX Runtime 格式与运行时生态成熟，支持 CPU、GPU 与多种 Execution Provider。
NVIDIA GPU 上追求固定模型的低延迟、高吞吐 ONNX + TensorRT 或 TensorRT 能针对 NVIDIA GPU 构建高度优化的推理 engine。
仅在 PyTorch/Python 服务内推理，先快速尝试优化 torch.compile 改动较小，便于直接在现有 PyTorch 代码中测试收益。
Apple 的 iOS / macOS 端侧应用 Core ML 与 Apple 平台、系统 API 和硬件加速路径结合紧密。
Android、嵌入式或资源受限端侧设备 LiteRT 或 ExecuTorch 都面向端侧；前者更偏 TensorFlow 生态，后者更贴近 PyTorch 工作流。
Intel 硬件为主 OpenVINO 面向 Intel CPU、GPU、NPU 的部署与优化工具链。
本地、离线、量化 LLM GGUF + llama.cpp 模型文件与运行时生态对量化、本地资源占用有较多针对性优化。
LLM 在线服务、高并发生成 vLLM、SGLang、TensorRT-LLM 除模型计算外，还会专门优化批处理调度与 KV Cache。
