0.2 GPU 体系结构（上）：编程模型与 wavefront 执行

这个小节，以最简单的情况讲述了AMD并行计算的实现机制，我的感觉就是将单线程顺序执行的重复任务以一种合适的机制映射到支持并行计算的硬件设备上，辅以并行计算软件层面的实现机制以并行的形式来执行单线程顺序执行的重复任务。

0.2.1 GPU计算的基本流程

不论是NVIDIA GPU还是AMD GPU，使用GPU做（并行）计算的大致流程都是：程序从 CPU （只能由CPU发起）上开始运行，准备输入，把数据放到 GPU 可以访问的位置，调用 GPU 完成计算。GPU 算完后，CPU 再取回结果。

GPU执行计算的具体内容放在一个函数内，这个函数叫核函数（Kernel）。CPU 提交这次 GPU 计算的动作，叫启动（Launch）。一次启动可以让许多线程（Thread）执行这个核函数，可以简单把每个线程看作是核函数的一次具体执行，GPU上的并行计算机制创建多个线程并行执行这个核函数，每个线程中执行核函数时会获取属于自己的数据进行计算。

在使用GPU做计算的过程中，CPU端一般叫做主机端（Host），GPU端一般叫做设备端（Device）。

线程也不是显卡上专属于它的一颗小处理器，它是一个软件术语。我们可以向GPU申请创建多个线程（针对特定的GPU，有一个线程上限），GPU 再利用有限的硬件资源安排执行。提交了多少份工作，和某一时刻有多少份工作正在执行，是两回事。

0.2.2 线程的组织与执行

线程块与网格

HIP 把一组线程称为线程块（Block）。启动 kernel 时，我们指定“每块多少个线程”和“一共多少块”。同一次启动的全部线程块，合在一起叫网格（Grid）。

为什么要创建线程块这个概念与机制： - 一方面，硬件可以把不同块安排到可用的资源上，不必等整个任务的所有线程都能同时执行。 - 另一方面，同一块内的线程可以在需要时交换数据、一起等待某个步骤完成。例如，把一批数合成一个和时，块内线程就可能要协作。

因此，Block 是组织一组线程工作的单位，Grid 是这次启动的全部工作集合。

线程块内的 wavefront

为了方便资源管理与计算，其实一个线程块内还可以继续把线程划分为不同的波前（Wavefront，简称 Wave），这样每个Wavefront包含多个不同的线程，此时Wavefront中每个线程叫做一个通道（Lane）。一个 Block 里的多个 Wavefront 不必同时开始或结束。

为什么要创建wavefront这个概念与机制： - GPU 可以让同一 Wavefront 中当前参与执行的线程，共同执行一条指令，各自使用自己的数据。

分块和组成 wavefront 也有不同的作用：Block 规定哪些线程归在一起、可以协作；Wavefront 则把块内线程组织成共同执行指令的小组。

启动 kernel 时指定块数和每块线程数；GPU 按这个 kernel 采用的 wave 大小（这是个相对固定的值）组织执行，不需要再单独指定“启动几个 wavefront”。不同 Block 的线程不会拼成同一个 wavefront。

随堂问题：同一个 kernel 启动出许多线程，它们是各执行工作单的一步，还是各执行一遍工作单？一个 Block 有多个 wavefront，是否说明多出了新线程？ 回答：各执行一遍工作单，即执行核函数kernel中设定的逻辑；没有多出新线程，只是把几个线程划分为同一个Wavefront，方便它们执行相同的指令。

0.2.3.1 线程块与块内线程的编号

既然每个线程在执行核函数时要读写属于自己的数据，那么就需要对每个线程进行区分。跟国家行政单位或军队编制单位等拥有明显的上下级组织机构类似，要先定位一个上级机构组织，才能定位到其下属的下级机构组织。

所以说，在AMD GPU编程中，要标识一个线程，要先标识一个线程块。对于一次启动创建的所有线程块与线程而言，每个线程块拥有一个唯一的编号，线程块内的每个线程拥有一个唯一的编号，但不同线程块的线程编号从0开始、所以可能会相同。

如果给定一个线程块编号，并给定此线程块编号对应线程块中的线程编号，就可以唯一确定一次启动中创建的所有线程中某一个线程，这样就可以把将所有线程区分开来了。

0.2.3.5 线程分组与硬件执行单元

到目前为止，我们已经学习到 AMD GPU编号内线程相关的组织形式：“Grid → Block → Wavefront → Thread”，也知道了具体每个线程如何获取唯一标识读写属于自己的数据了。

一个 Block 或 wavefront 是一组线程工作，是软件层面的概念；要把它们与硬件设备区分开（虽然它们有联系），并不表示显卡上为一个 Block 或 wavefront 单独准备了一块同名硬件。

在 AMD RDNA 的语境里，先区分下面几个名字：

名字 本章先掌握的含义
单指令多数据执行单元（Single Instruction, Multiple Data，SIMD） 用一条向量指令处理一组 lane 的数据；这里的“多数据”对应各 lane 不同的输入
计算单元（Compute Unit，CU） 包含执行单元及相关资源的一层硬件组织
工作组处理器（Workgroup Processor，WGP） RDNA 中包含 CU 的更外层组织，也与同一工作组的放置范围有关

下图展示了工作分组与硬件单元的关系。图没有规定单元数量或某次运行的调度顺序，也不表示一个 block 独占一个硬件单元。 从上图可以看出（实际上也确实是这样）：软件上的一组工作需要落到硬件资源上执行。AMDGPU 文档 LLVM AMDGPU 执行模型 对工作组给出了放置约束：同一工作组的 wavefront 在同一 WGP 中执行；更细的执行范围还与 CU/WGP 模式有关。详情见文档。

在进行接下来更细致的学习之前，先有这样的认知：逻辑上创建了多少线程，与物理实际上此刻能执行多少工作，是两个问题。 后者会受到其他很多资源（如寄存器、共享存储和数据等待等等）的制约。就是说，对于一份工作而言，当设定好了主机端的逻辑与设备端核函数逻辑后，某时刻GPU上真正能并行执行的线程数有一个理论上限，实际线程数会在这个理论线程数左右，无法做到有远超此理论线程数的线程在执行。

同一个工作组内的不同线程/通道也可以按条件决定是否执行。同一 wavefront 内的线程选择了不同控制路径，这种情况专业术语叫分支发散（Branch Divergence）。

  • 启动时指定块数和每块线程数，全部块组成 Grid；块内线程按 wave 大小组成执行小组。Lane 表示线程在 wavefront 内的位置。

  • Block 和 wavefront 是线程的分组，CU、WGP 和 SIMD 是承接这些工作的硬件。提交的线程总数不等于某一时刻正在执行的线程数。

0.3.2 Wavefront 的访存组织

前面说明过：同一个wavefront内不同lane对应的线程，执行完全相同的指令。 就是说，对于同一个wavefront，当它执行一条数组读取指令时，这个wavefront内的所有线程分别有自己要读取与使用的数组元素，此时AMD HIP编程的实现是，去把这些线程要读取的数据所在数据块（每个数据块可能包含多个数组元素，根据自定义数据结构与数据类型而异）读取来，但实际上最后可能只使用其中一部分数据。

打个比方： 某次任务中，其中一个wavefront包含多个线程，下图只画出其中4个。由于自定义数据结构与数据类型的不同，可能会出现下图中”相邻位置“、”分散位置“两种情况（可以把下图中的教学组看成一个数据块）： 在GPU显存中，数据是按数据块进行组织与访问。一个数据块的大小一般来说是相对稳定的，就相当于格式化一块磁盘会将选定其数据块大小一样，所以说每个数据块中能够保存的数据是有限的。

即存储系统通常按一定大小的数据块组织和服务访问。线程需要一个元素，不意味着底层只处理这一个元素。请求集中时，同一段数据（一个或少数几个相邻数据块）就可能满足多个线程；请求分散时，可能需要涉及更多数据块，其中只有部分元素被这批线程使用。

对于”相邻位置“这种情况，因为自定义数据结构设计地科学合理（与单个数据块刚好匹配：可能是一样大，也可能是几个结构体只好凑成一个数据块等情况），同一个wavefront的多个线程需要的数据，存储在一个或少数几个数据块内，访问这一个或少数几个数据块即可。 对于”分散位置“这种情况，同一个wavefront的多个线程需要的数据会更分散地存储在不同的数据块中（典型的情况是：一个数据块中只有很少一部分数据是线程所需要的，把整个数据块读取过来浪费了寄存器、带宽等资源），此时就需要读取多个数据块，造成临时存储空间与带宽等资源的浪费。

硬件把同一 wavefront 的访存请求尽量合并处理，这个过程称为合并访存（Memory Coalescing）。所以在此背景下，在GPU编程中，不仅仅是要“写 Kernel 函数”，更核心的功夫在于设计数据在显存中的排布方式（尽量连续与对齐），以及合理分配线程的工作任务（让相邻线程恰好去读连续的数据），从而把分散的访存请求压缩成尽量少的数据块传输，提高合并访存的效率。

访存地址由我们编写的程序决定，实际怎样合并由硬件完成。

数据读取还存在另一种机会：需要的数据可能已经有一份副本留在更靠近计算部件的存储中。这种由硬件管理的存储叫缓存（Cache）。找到所需副本叫命中（Hit），没找到则继续向后面的存储层级请求。缓存通常按数据块保存副本，这些数据块称为缓存行（Cache Line）。

合并访存关注的是一批请求所需数据的位置是否相邻、分布在一个或少数几个相邻的数据块中；缓存关注的是请求所需数据是否已在更靠近计算部件的存储中存在副本。

同样都是直接从中取值，缓存是由硬件管理，保存访问过的数据副本；而共享区LDS则是由程序在软件层面来安排，用于数据交接与共享。

0.3.4 访存等待与指令调度

一个wavefront被调度执行后，可能并不会一直占用系统的计算资源执行下去直到结束。因为它可能会在某个步骤发生读写请求，此时它申请读取或写入动作可能并不会立刻成功结束（比如申请读取数据时，但数据并不会立刻返回来），此时，如果后续步骤依赖此步骤的读写结束，wavefront就要等待，具体为是状态变更为“驻留”。

由此引发对wavefront的几种状态的探讨：

状态 可以怎样理解
驻留（Resident） 工作已经获得相应片上资源，但因为数据等未准备就绪无法被立刻调度以执行。但其状态保留在硬件中
就绪（Ready / Eligible） 满足继续执行所需的条件，可以被选择
执行（Executing） 当前获得了执行机会，正在发射或执行相应指令

回到上述4个数求总和的示例，wave0的线程甲读取数据过程，wave0 已经发出请求，但输入还没有返回，依赖它的加法暂时不能执行。如果同一计算资源上还有 wave1 的指令已经就绪，硬件可以先安排 wave1。

这种选择就绪指令放到执行资源上真正执行的过程由 GPU 的调度器（Scheduler） 发起。

wave0 等待时，它的临时值和执行状态仍然保留；选择 wave1 不需要把 wave0 当作已经完成，也不需要由 CPU 手动切换这两个 wavefront。

这种用其他就绪工作利用等待时间的方式，称为延迟隐藏（Latency Hiding）。wave0 的读取并没有因此更早返回，只是执行资源在这段时间有机会继续做别的工作。如果其他 wavefront 也都在等待，或者它们需要的执行资源正忙，仍然可能出现资源空闲。AMD GPUOpen：Occupancy explained

  • 输入、输出数组与计算使用的临时值各有用途。寄存器保存值，执行单元使用这些值运算；得到结果后仍要写回输出。
  • 看访存要观察同一 wavefront 的地址排列。集中请求更有机会合并服务，缓存则可能提供已有的数据副本。

0.3 GPU 体系结构（下）：片上资源与数据通路（旧）

0.3.1 一次加法的大致过程

AMD GPU上要执行一次计算，首先要从全局内存（显存。同一事物从不同角度的不同叫法）或缓存（如果能在缓存中找到对应的数据）读取数据加载到临时存储（一般是寄存器），然后把临时存储中的输入数据进行计算得到结果，再将结果写回到全局内存（显存）中。

另外在全局内存（显存）的外面，还有一个CPU使用的内存。就是说计算前有时需要从CPU使用的内存中将复制到全局内存（显存）中，计算完成后可能需要将全局内存（显存）中的结果再又复制回CPU使用的内存中。

0.3.2 数据的存取、管理与缓存

0.3.2.1 向量通用寄存器与标量通用寄存器

同一个 wavefront 下的不同lane可以存取不同的数据，就是说同一个 wavefront 下的不同lane 有自己独有存取数据的存储空间，这是通过 向量通用寄存器（Vector General-Purpose Register，VGPR） 来实现的。 同一个 wavefront 下的不同lane 在同一个向量通用寄存器编号下有自己的独有的寄存器分量（即不同lane在同一寄存器编号下可以有相同的变量名，但实际上保存不同的值）。

此外，同一个wavefront内有共享的数据，它们在整个wavefront范围内是共用的，比如数组的基址。这类数据叫做标量状态，是通过 标量通用寄存器（Scalar General-Purpose Register，SGPR） 实现的。同一个wavefront 下的不同线程可以基于数组基址，再结合通道偏移量来找到自己要存取的数组数据。

0.3.2.2 局部数据共享存储与数据缓存

对于同一个工作组的不同线程（不管是不是属于同一个wavefront），如果要共享同步数据，AMD也在硬件上专门开辟了一块区域。这块区域叫做 局部数据共享存储（Local Data Share，LDS） ，在 HIP 中通过 __shared__ 进行声明。

前面提过，程序当然是能够访问全局内存的，但刚刚访问过的/经常访问的 某全局内存数据会被放到缓存（Cache）中，方便后续快速访问（系统认为用户接下来需要继续使用），而不必再重新从全局内存中读取。缓存（Cache） 是由硬件进行管理的，如果某请求的数据能够在缓存中找到，则称为一次命中（Hit）。

0.3.3 向“合并访存”靠近

在GPU显存中，数据是按数据块进行组织与访问。一个数据块的大小一般来说是相对稳定的，就相当于格式化一块磁盘会将选定其数据块大小一样，所以说每个数据块中能够保存的数据是有限的。

这样的机制下，想要访问到某个数据，其实是先访问数据所在的整个数据块，然后再从数据块中取出我们想要的某个（些）数据。试想如果我们真正想要的数据分散在不同的数据块就会造成如下现象：先找到并传输所有相关的多个数据块，然后这些数据块只分别取出其中某个或某几个数据，这样造成了带宽的很大浪费，也增加访问的时间与效率。

显存的带宽是极其宝贵的，以 64 个工人（Lane）搬取货物（读取数据）为例说明合并访存的必要性：

  • 合并访存成功时：64 个工人需要的东西都在同一个箱子里，卡车送来 1 个箱子，所有人同时拿到东西（合并访存，效率极高）。==【64 个线程的请求落入同一个数据块，GPU 只需要向显存（VRAM）发起 1 次 内存事务（Memory Transaction）就能把数据一次性搬运过来。】==
  • 完全散乱时：64 个工人每人要的东西都在不同的仓库里，卡车必须跑 64 趟去搬 64 个箱子，而每个箱子装满数据，工人却只拿走了其中 4 个字节，造成严重的带宽浪费。==【GPU 的内存控制器不得不向显存发起 64 次 独立的内存事务。】==

程序员该如何解决这个问题？（数据结构与访问模式优化） 既然待读取的数据位置决定了合并访存的成败，那么在 GPU 编程中，程序员的责任就是主动把数据“整理”成便于相邻线程连续读取的格式。最典型的优化手段就是 SOA 与 AOS 的转换：

  • AOS (Array of Structures，结构体数组，对 GPU 很不友好)：

    如果每个线程负责一个粒子并读取其 x 坐标：

  • Lane 0 读 particles[0].x (地址 0)

为此，在GPU编程中，不仅仅是要“写 Kernel 函数”，更核心的功夫在于设计数据在显存中的排布方式（尽量连续与对齐），以及合理分配线程的工作任务（让相邻线程恰好去读连续的数据），从而把分散的访存请求压缩成尽量少的数据块传输。

当同一个wavefront中不同线程访问数据时，我们应该尽量保证这些数据存储在相同/相邻的数据块。把同一 wavefront 的地址请求组织得便于硬件合并处理，这就是 合并访存（Memory Coalescing） 要解决的问题。当同一个wavefront中不同线程待访问的数据紧凑地分布在相同或相邻的数据块中时，硬件就能将其打包为极少数的内存事务（Memory Transactions），这就是合并访存（Memory Coalescing）。这将极大提升带宽传输、访存效率。

0.3.4 LDS的作用与工作流程

同一个工作组的多个不同的线程需要交换与复用某个（些）数据，就需要用到局部数据共享存储（LDS）。其中的多个线程按照约定流程将自己负责的那部分内容写进LDS，并在写入后更新 屏障同步（Barrier） 标识，以告诉其他线程“我已经将我负责的部分写入更新了，你们可以往下执行流程了”。当所有相关线程都写入自己负责的部分并更新 屏障同步（Barrier） 标识，待屏障解除后，各个线程再按照算法逻辑，安全地读取 LDS 中由自己或其他线程写入的数据进行后续计算。

通过这种“协同加载 + LDS 共享 + 屏障同步”的模式，原本需要多次访问慢速显存的重复操作，被转化为对高速 LDS 的直接访问，从而大幅提升了计算效率。

0.3.5 wavefront的调度与执行

0.3.5.1 wavefront 三种状态：驻留、就绪和执行

一个wavefront被调度执行后，可能并不会一直占用系统的计算资源执行下去直到结束。因为它可能会在某个步骤发生读写请求，此时它申请读取或写入动作可能并不会立刻成功结束（比如申请读取数据时，但数据并不会立刻返回来），此时，如果后续步骤依赖此步骤的读写结束，wavefront就要等待，具体为是状态变更为“驻留”。

由此引发对wavefront的几种状态的探讨：

状态 可以怎样理解
驻留（Resident） 工作已经获得相应片上资源，但因为数据等未准备就绪无法被立刻调度以执行。但其状态保留在硬件中
就绪（Ready / Eligible） 满足继续执行所需的条件，可以被选择
执行（Executing） 当前获得了执行机会，正在发射或执行相应指令

在整个系统中，可能会同时存在多个未完成的wavefront，硬件中可能保留其他wavefront的状态，如果当前wavefront因为数据未准备就绪从“执行”状态变更为“驻留”，那么其他处于”就绪“状态的wavefront就可能被调度到以执行。一般来说，系统总是尽可能让所有资源处于不停歇地工作中。

下图展示了系统中两个wavefront在未结束前具体状态的变更：

上图中，wavefront A等数据需要一个过程，在这段时间内，wavefront A其实是相当于被卡着、等待数据的返回。期间，计算资源并没有闲着，它的使用权被交给wavefront B，保证系统中其他wavefront继续正常执行，从外面看来，整个系统还是处于工作状态，好像wavefront A等待数据期间的延迟被隐藏了一样，就个现象叫做延迟隐藏（Latency Hiding）。

有时存在极端的情况， 即如果wavefront等待数据期间，系统中不存在处于“就绪”状态wavefront，那么系统中的计算资源就要空闲下来了。

0.3.5.2 wavefront 占用率

每份工作从开始执行到未结束期间，系统要保留其它的临时值、执行状态等，这些东西都要要占用GPU内部有限的片上资源（如寄存器、LDS等）。 所以说每份使用与临时保留的资源要恰到好处，不能太多，也不能太少。太多会导致GPU上能够同时容纳的工作份数减少，太少的话可能造成频繁的读取、降低工作间共享数据的可能性。

以多个wavefront来说，GPU上的片上资源上限是固定的，如果单个wavefront的临时资源越多，则GPU上能够容纳的wavefront个数就越少。实际工作中还是考虑到分配粒度与其他上限，实际上能够容纳的wavefront个数一般比“GPU总片上资源数/wavefront平均占用临时资源数”小。

在某个GPU任务中，可以计算出一个大致可用的wavefront 槽位（个数上限）。处于“驻留”状态的 wavefront 个数 除以 可用的wavefront 槽位，再乘以100%，就是wavefront 占用率。

\[\text{wavefront 占用率} = \frac{\text{驻留 wavefront 个数}}{\text{可用的wavefront 槽位}} ✖️ \text{100\%}\]

当系统中 wavefront 占用率高时，平均来说处于就绪状态的wavefront量也相对高，此时可供选择的wavefront相对多，理论上计算资源可能会处于忙碌状态、提升其利用率，但实际工作中要警惕它们等待同一或同一类受限数据，此时可能造成计算资源处于饥饿状态、程序执行时间增加。

相对地，增加单个wavefront保留的临时资源，会使用系统中容纳wavefront数减少，从而减少wavefront占用率，就绪状态的wavefront可能减少了，但却会增加 wavefront 复用数据、内合并访存的可能性，从而提升程序执行效率。

所以是提升还是减少wavefron占用率，不能一概而论，要根据实际的内核设计与程序执行效果来分析与优化。

0.4.4 解释测量结果

PyTorch 向量加法示例中，每次加法需要处理的有效数据量为 3个float32数，即3 * 4 = 12 Bytes。假设示例需要处理的数组长度是N，那么整个示例算法需要处理的有效数据量为：12 * N 。

再设定 CPU/GPU 上执行计算的耗时是 t （单位：ms），那么得到有效带宽： \[ BW_{\mathrm{effective}}=\frac{12N}{t}. \]

有效带宽回答的是“每秒完成了多少算法所要求的数据处理”，并没有测出显存实际传输了多少字节。缓存、访存粒度和写入路径都可能让物理流量与 不同。

上述公式再变更下形式与单位，得到如下计算公式（结果单位是：GB/s）： \[ BW_{\mathrm{effective}} =\frac{B_{\mathrm{effective}}\times10^{-6}}{耗时\_ms} \]
